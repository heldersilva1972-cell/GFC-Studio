# Secure Controller Migration Guide (Remote Network)

**Objective:** Move the Card Access Controller to a newly remote location while maintaining secure communication with the Web App, **without changing the Controller's hard-coded IP address.**

## The Core Problem: "The Zip Code Conflict"
*   **Your Server** is likely on the `192.168.1.x` network.
*   **Your Controller** is fixed to `192.168.1.x`.
*   **The Problem:** If you move the controller to a remote site, your Server will still try to find it "inside the building" because of the matching IP address. It will never send the data out to the URL/VPN.
*   **The Solution:** We will create a **"Ghost" Alias IP** (`192.168.55.72`) in the Web App. The Server will send data to this Ghost IP, forcing it through the VPN, where the remote Router will translate it back to the Real IP (`192.168.1.72`).

---

## Phase 1: Preparation (Do this BEFORE moving the controller)

**Goal:** Remove security locks that might block the connection once the move happens.

1.  **Log in to the Web App** and go to **Controllers -> [Your Controller] -> Network**.
2.  **Locate "Allowed PC IP".**
    *   Currently, it is likely set to `192.168.1.50` (or similar).
    *   This setting tells the controller: *"Ignore everyone except this specific computer."*
    *   When we move to VPN, the traffic might look like it's coming from a different "Tunnel IP," causing the controller to ignore valid commands.
3.  **Action:**
    *   **Clear the field.** Make it empty.
    *   **Click "Apply to Controller"** (Push to Hardware).
    *   *Verify:* Ensure the controller accepts the change.
4.  **Save to DB:** Click "Save" to ensure the database matches.

---

## Phase 2: Server-Side Setup (The "Hub")

**Goal:** Set up the secure encrypted tunnel (WireGuard) and the routing for the "Ghost" IP.

### 1. Install WireGuard
*   Download and install the official [WireGuard for Windows](https://www.wireguard.com/install/) on your hosting Server.

### 2. Configure the Tunnel
*   Create a New Tunnel (e.g., `GFC_VPN`).
*   **Configuration Block (Paste this into WireGuard):**
    ```ini
    [Interface]
    # This is the Server's IP inside the VPN tunnel
    Address = 10.8.0.1/24
    ListenPort = 51820
    PrivateKey = (Auto-Generated by WireGuard - Do not change)

    [Peer]
    # This represents the Remote TP-Link Router
    PublicKey = (You will copy this from the TP-Link WireGuard menu later)
    
    # CRITICAL: Routing Logic
    # 10.8.0.2/32 -> The specific tunnel IP of the router
    # 192.168.55.72/32 -> The "Ghost IP" you will use in the Web App
    # This tells Windows: "If traffic is for the Ghost IP, shove it into this tunnel."
    AllowedIPs = 10.8.0.2/32, 192.168.55.72/32 
    ```

### 3. Firewall Rule (Windows & Network)
*   **Network Router:** Forward **UDP Port 51820** to your Windows Server's LAN IP (`192.168.1.x`).
*   **Windows Firewall:** Ensure WireGuard is allowed through the Public/Private firewall profile.

---

## Phase 3: Remote Site Setup (The "Spoke")

**Goal:** Configure the TP-Link ER605 to host the controller and translate the "Ghost IP" to the "Real IP".

### 1. Network Wiring & "The Fixed IP Problem"
*   **The Constraint:** Your controller is hard-coded to `192.168.1.72` and likely expects a Gateway of `192.168.1.1`.
*   **The Setup:** You MUST configure the TP-Link LAN to match this expectation, or the controller will essentially have no internet/network access.
*   **Action:**
    1.  Login to the TP-Link Router (Default `192.168.0.1`).
    2.  Go to **Network -> LAN**.
    3.  Change the IP Address to **`192.168.1.1`**.
    4.  The router will reboot. You must now access it at `192.168.1.1`.

### 2. WireGuard Client Setup (On TP-Link)
*   Go to **VPN -> WireGuard**.
*   **Create Interface:**
    *   **Name:** `S2S_VPN`
    *   **Private Key:** (Click Generate) -> **COPY THE PUBLIC KEY** (You need this for Phase 2 Step 2 on the Server).
    *   **IP Address:** `10.8.0.2` (This is the router's ID in the VPN).
    *   **Listen Port:** `51820`
*   **Add Peer (Your Server):**
    *   **Public Key:** (Copy from your Windows Server WireGuard Interface).
    *   **Endpoint:** `Your_Office_Public_IP:51820`
    *   **AllowedIPs:** `0.0.0.0/0` (This creates a default route back to the server).
    *   **Persistent Keepalive:** `25` (Crucial to keep the connection alive through NAT).

### 3. The Routing / Translation Step (Firmware Specific)
*Since the Host sends to `.55.72` and the Controller listens on `.1.72`, the TP-Link must bridge this gap.*

**Method: The Static Route Trick**
This tricks the router into accepted the "Ghost" packet and handing it to the local device.
1.  Go to **Transmission -> Routing -> Static Routes**.
2.  **Add New Route:**
    *   **Destination Network:** `192.168.55.72` (The Ghost IP)
    *   **Subnet Mask:** `255.255.255.255` (Match only this specific single IP)
    *   **Next Hop:** `192.168.1.72` (The Real Controller Address)
    *   **Interface:** LAN
3.  *Check:* If the router refuses this route because they are on different subnets, proceed to **Method B**.

**Method B: "Disable NAT" Rule**
1.  Go to **Transmission -> NAT -> Disable NAT** (or "NO-NAT").
2.  Create a rule:
    *   **Source:** `10.8.0.0/24` (The VPN Tunnel traffic)
    *   **Destination:** `192.168.1.0/24` (The Local Controller traffic)
    *   **Status:** Enabled.
3.  *Why:* This ensures the packet acts like a local LAN packet, allowing the controller to reply to it without the router mangling the address headers.

---

## Phase 4: Web App Configuration (The Final Link)

**Goal:** Re-point the Web App to the new secure tunnel entrance.

1.  Navigate to **Controllers -> Network**.
2.  **Static IP Address:**
    *   Change this from `192.168.1.72` to **`192.168.55.72`**.
    *   *Logic:*
        *   App sends to `192.168.55.72`.
        *   Windows OS says: "Foreign IP! Send to WireGuard Interface!"
        *   WireGuard encrypts and sends to TP-Link.
        *   TP-Link sees `192.168.55.72` and uses the Static Route to hand it to `192.168.1.72`.
3.  **Gateway:**
    *   Update this to `192.168.1.1` (Just for documentation, does not affect routing).
4.  **Confirm Settings:**
    *   **Allowed PC IP:** MUST BE EMPTY.
5.  **Action:**
    *   **Click ONLY "[Save]" (or Save to DB).**
    *   **WARNNING:** DO NOT click "Apply to Controller". It will fail and throw an error because the old IP is unreachable.

---

---

## Phase 5: Verification

1.  **Ping Test:**
    *   On the Windows Server, open PowerShell.
    *   `ping 192.168.55.72`
    *   If you get a reply, the VPN + Translation is working perfectly.
2.  **Web App Test:**
    *   Go to **Controllers -> Settings -> Status**.
    *   The indicator should turn **Green (Connected)**.
    *   Try unlocking a door.

**Summary:**
You are tricking the Server into thinking the controller is on a new network (`.55.x`), while the controller sits happily on its old network (`.1.x`) at the new building, protected by the VPN.
